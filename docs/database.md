# Database

DataVault uses PostgreSQL and Drizzle ORM. UUID primary keys are generated by PostgreSQL.

## Table groups

- Identity: `users`, `accounts`, `sessions`, `verifications`, `two_factors`
- Tenancy/RBAC: `organizations`, `organization_members`, `roles`, `permissions`, `role_permissions`, `user_roles`, `organization_invitations`, `saved_views`
- Universal records: `saved_records`, `capture_sources`, `evidence_snapshots`, `attachments`, `processing_jobs`
- Grouping: `vaults`, `tags`, `saved_record_tags`
- Docs: `notes`, `note_revisions`, `user_note_prefs`, `note_ai_previews`
- AI: `ai_credit_periods`, `ai_credit_ledger`, `ai_usage_events`, `ai_consents`, `ai_response_cache`, `ai_global_counters`, `record_embeddings`
- Operations: `audit_logs`, `extension_auth_codes`, `extension_sessions`, `extension_refresh_tokens`, `idempotency_keys`, `rate_limit_buckets`

`saved_records` is the durable universal layer. A browser capture is filed as an article, a quote, a statistic, a definition, a person, a product, an event, or one of the plain formats a clip can arrive in, and it stays readable even when it cannot be classified at all.

`notes` holds a doc. Its content is the rich text the editor works with, stored as JSON, with the plain text kept beside it for search and summaries. A doc carries a version number, so two people cannot overwrite each other, and a clip count and the time of the last piece.

`note_revisions` keeps the earlier versions of a doc. Only the last thirty versions of each doc are kept, and a version is only stored every ten minutes while the user is typing.

`note_ai_previews` holds an answer the model gave for a doc, waiting to be applied. The answer is kept on the server so that applying it does not need to ask the model again, and it carries the version of the doc it was made from, so it is never written over work that happened in the meantime.

`ai_credit_periods` holds the allowance a person has for one day. The row belongs to the person rather than to a workspace, because the allowance belongs to the person: a second workspace is not a second allowance.

`ai_global_counters` holds the two numbers the whole product shares, the requests made today and the people who have made one. They are about everybody, so they cannot live in a table that is scoped to one person.

`record_embeddings` holds the numbers that say what a saved item is about. Two texts that mean the same thing have numbers that are close together, so a search can find an item by what it is about rather than by the words it uses. The numbers are kept in a plain list of numbers rather than in the vector type of the `pgvector` extension, so that the search works on any PostgreSQL; the `datavault_cosine` function does the comparing. The table is the same either way, so the extension can be used later without changing anything else.

## Constraints and indexes

- Organization-scoped identifiers and saved-record links are unique.
- Organization, date and type indexes support the common lists.
- PostgreSQL trigram indexes cover titles and the text that was captured.
- `pg_trgm` and `unaccent` are enabled by the first migration.
- `saved_records` carries a `search_vector` column, which is a generated column: PostgreSQL writes it out itself, so it can never fall behind the text it was made from. A title counts for more than a description, and a description for more than the text that was captured, and a GIN index on the column is what makes the search quick.

## RLS

Tenant tables have a `tenant_isolation` policy comparing `organization_id` with `current_setting('app.organization_id', true)`. The credit tables have an `account_isolation` policy comparing `user_id` with `current_setting('app.user_id', true)`, because the allowance belongs to the person rather than to the workspace.

The rules are **forced**, so they apply to the owner of the table as well. Without that, a connection made as the owner would simply ignore them, and the isolation would be nothing but a habit in the application code. API service transactions call `set_config(..., true)` for both values before the business queries.

`ai_response_cache` holds model answers that are shared by everyone, and it has no workspace or person in it, so it has no rule to apply. `ai_global_counters` holds two numbers about everybody, for the same reason.

### The two roles

The application does not connect as the owner of the tables. It connects as a role of its own, `data_vault_app`, which is not a superuser, does not bypass the rules, and may read and write the tables but not change them. The migrations run as the administrative role in `DATABASE_ADMIN_URL`, which is the only role that may create and change the tables.

```bash
bun run db:create-role
```

The script creates the role if it is missing, sets its password from `DATABASE_URL` (or `DATABASE_APP_PASSWORD`), gives it the grants it needs on the tables of the database, and gives the same grants for the tables that come later. It is chained after the migrations, so a new table is usable as soon as the migration has run.

Because the role is subject to the rules, a query that does not say which workspace or which person it is working in sees nothing at all. `bun run db:inspect-rls` shows which tables have the rules and which policies they carry, and it fails when a table that holds business data is missing them.

One rule is narrower than the rest. The credit ledger follows the person, so the server could not see whether a request key had been used by another account. The `idempotency_claim` policy lets exactly one row through, the one that holds the key the server is asking about, and it only applies to reading. The key is named in `app.claim_key` for the length of the transaction.

## Migrations and seed

```bash
bun run db:migrate
bun run db:create-role
bun run db:bootstrap
bun run db:check
```

`DATABASE_URL` names the database and the application role. `DATABASE_ADMIN_URL` names the same database as the administrative role, so the migrations reach the right one. A missing database is created through the maintenance database.

Review generated SQL before production deployment. `db:bootstrap` only ensures the global permission catalog exists.
